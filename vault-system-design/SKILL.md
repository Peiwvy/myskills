## 上游依赖

本 skill 改的是 vault 结构。改之前需要知道「改什么、怎么改」（操作参照），改之后需要知道「怎么追踪变更」（流程约束）。两类依赖不同。

### 操作参照：改之前读，知道当前结构长什么样

这些是**数据依赖**——不改它们，只是读取它们来理解当前状态：

- [[系统方法论#两个操作层级]] — 概念来源。操作结构 vs 操作要素的区分
- [[结构设计]] — **当前结构长什么样**。目录树 + 流转主链。relate 做 MECE 分桶的权威参照——你总得先知道现在有哪些桶，才能重新分桶
- [[目录规范]] — **新建/修改目录时 CLAUDE.md 怎么写**。specify 的对齐标准——不改目录规范本身，但产出的目录必须符合它
- [[页面规范]] — **每类页面长什么样**。全部 schema。specify 的格式基准——不改 schema 本身（除非用户明确要求），但产出的页面必须符合 schema

### 流程约束：改之后遵循，知道怎么追踪变更

这些是**流程依赖**——结构变更不是改完就完了，必须留下可追溯的记录：

- [[演化协议]] — **变更必须走的流程**。五阶段闭环：Brainstorm → proposal → Plan → design/tasks → Execute → Verify+Archive。本 skill 执行的结构变更，最终要落成 openspec/ 里的一个 change 文件夹
- [[演化协议#4-openspec-层级路由]] — **变更落在哪个 openspec/**。改单个项目 → 该项目自己的 openspec/；跨项目 / vault 全局 → Z98-Design/openspec/。规则在 演化协议里，不依赖外部实施文件

> 简单说：操作参照告诉本 skill「改成什么样」，流程约束告诉本 skill「改完之后怎么交差」。

# 结构操作统一入口

管辖区**操作结构层**。vault 结构二分为**节点间关系**（拆分+连接）与**节点定义**，分别对应 `reference/relate.md` 和 `reference/specify.md`。

- 概念定义：[[系统方法论#两个操作层级]]
- 操作要素日常：`/vault-distill`（不在本 skill 范围）

## 子流程索引

|| 退化信号 | 加载 | 接入点 |
|---|---|---|---|
| 找不到 / 放不下 / 连不起来 | `reference/relate.md` | 拆分走 §拆分子流程；连接走 §连接子流程 |
| 看不懂 | `reference/specify.md` | Stage 1：需求澄清 |
| 多面耦合 / 全新架构 | 本文 §跨层统筹 | — |

**设计原则**：

- 本文件**只做分诊 + 跨层统筹**，不重复子手册的操作细节
- 单层退化必须切换到对应 reference/，不在主文件里解决
- 子手册之间不直接跳转；跨层问题统一回本文件协调

## Step 1：快速分诊

**信号→动作映射**：

| 用户说的 / 观察到的 | 退化面 | 加载 |
|---|---|---|
| 找不到、放不下、连不起来、归类、重组、MECE、双链断了、孤立页 | 节点间关系 | `reference/relate.md` |
| 看不懂、schema、规范化、模板统一、命名、frontmatter 对齐 | 节点定义 | `reference/specify.md` |
| 以上混合出现，或"整体结构要重新设计" | 多面耦合 | 本文件 §Step 3 |

> **边界**：本 skill 只操作**结构**（目录/schema/文件分桶，按元数据分类），不读页面正文。若需**读懂多篇 narrative 的内容**做事实级收敛（找公约数、抽 hub、薄化叙事）→ 那是**内容层**工作，走 `/vault-converge`，不在本 skill 范围。

**例外快速路径**：用户以明确词汇直接点明工作类型（"帮我归类 KF20-Inbox" / "给这批讲者设计 schema"）→ 直接按语意定位退化面，跳过诊断。

## Step 2：加载子手册执行

- **单面退化** → 用 `Read` 工具读取完整 reference/ 文件后执行；子手册的终止条件即本 skill 在该路径的终点
- 子手册中途识别到**跨面问题** → 告知用户，回到本文件协调切换

## Step 3：跨层统筹（仅多面退化时）

仅以下情形本文件继续：

- **多面耦合**：两个以上面同时退化
- **新建系统架构**：结构三面从 0 设计

对每个改进点，按"思考→执行→验证"模式：

1. **思考**：背景、目标、方案、风险、验证判据
2. **与用户确认方案**后执行
3. **执行**后验证结果

完成后按 [[演化协议]] 流程，将变更记录到对应 openspec/（单项目→项目 openspec/，跨项目→Z98-Design/openspec/）。

## 适用场景

- **归类 / 重组 / MECE 分类** → `reference/relate.md` §拆分子流程
- **双链修复 / 孤立页清理** → `reference/relate.md` §连接子流程
- **Schema 设计 / 模板统一 / 命名规范** → `reference/specify.md`
- **不确定问题出在哪一面** → 跑 Step 1 分诊
- **多面耦合的复杂重构 / 新建系统架构** → Step 3 跨层统筹

## 反模式

- ❌ 识别出单面退化后不加载 reference/，自己在主文件里临时写流程
- ❌ 把 reference/ 的细节复制回本文件（SSOT 必须保持）
- ❌ 跳过分诊直接给方案（没有诊断就没有分诊依据）
- ❌ 在子手册流程中途遇到跨面问题却不告知用户、擅自扩大范围
